# Подготовка к нагрузке около 5 000 одновременных игроков

В приложении добавлены настройки, снижающие накладные расходы при всплесках:

- входной TCP backlog HTTP-сервера — 8 192;
- повторные одновременные проверки подписки одного пользователя объединяются в один запрос;
- проверки Telegram используют общий пул соединений с ограничением в 100 соединений и кэш результата на 60 секунд;
- SQLite работает в WAL, ждёт блокировку до 10 секунд и использует ограниченный page cache;
- очистка per-user rate-limit бакетов не запускается полным проходом по словарю на каждом запросе.

## Обязательные настройки Linux

Backlog приложения ограничен системным `somaxconn`, а число соединений — лимитом открытых файлов. Для systemd-сервиса задайте override:

```ini
[Service]
LimitNOFILE=20000
```

И системный backlog (например, `/etc/sysctl.d/90-simka.conf`):

```conf
net.core.somaxconn=8192
```

Примените `sudo sysctl --system`, перезапустите сервис и проверьте `ulimit -n` для процесса.

Перед запуском на 5 000 пользователей обязательно проведите нагрузочный тест на целевом сервере и через тот же reverse proxy, что будет в production. Нагрузочное поведение зависит от CPU/RAM, диска, лимитов ОС, качества Telegram Bot API и доли одновременно выполняемых игровых операций. Первый вход каждого нового пользователя требует отдельной серверной проверки подписки у Telegram; общий пул защищает процесс от открытия тысяч лишних HTTP-коннекторов, но не отменяет лимиты и задержки Telegram.

SQLite и один процесс бота остаются узким местом для большого числа одновременных операций записи. Если нагрузочный тест показывает блокировки или растущую очередь, следующий архитектурный шаг — вынести API в отдельные workers и перевести общую базу на PostgreSQL. Нельзя просто запустить несколько копий бота с одним Telethon session-файлом и локальной SQLite.
